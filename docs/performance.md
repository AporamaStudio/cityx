# Web原型性能分析与3D实现约束

更新：2026-10-17。本文集中记录性能判断、测量边界与优化候选；原迁移进度仍见[todo](todo.md#3d视觉与动效接入2026-10-12用户要求记录)，历史验收见[verification](verification.md)。

## 优先级与实施状态

- **用户确定：视觉第一，性能第二，不能为了性能牺牲视觉效果。** 优化首先消除重复计算、无效检测、无贡献渲染和资源反复创建，保留当前镜头下应有的造型、灯光、云雾、人群、动效与信息可读性。
- **优化记录P0（2026-10-16，用户确定）**：所有性能优化必须在本文同步记录原因、实际改动、验证场景/指标、测量边界和已知副作用；没有测量就标记未测，不宣称收益。后续发现的回退及未覆盖场景也须补记，分析与建议不得写成已完成优化。
- 初始分析只更新文档；用户随后授权开始优化，已实现范围见末尾记录。下文未列入完成记录的调度、拾取和渲染方案仍是待实施建议。
- 性能优化服务于实际试玩：先解决自由旋转、拖动、选炮与夜间补防的卡顿。没有实测依据，不扩展成通用渲染框架、复杂模拟器或正式版产品工程。
- 既有路灯预算、视觉人数与像素比是当前实现事实，不是以后所有场景的固定上限，也不是默认继续降低的对象。有可感知视觉损失的减灯、减人、降分辨率、减特效或LOD切换，属于需要另行讨论的表现取舍，不作为性能修复默认纳入。

## 是否需要视觉帧和逻辑帧

**建议明确分开职责和时间，不新增两套独立计时循环。** 当前已有`requestAnimationFrame`驱动的显示循环、夜间离散战斗拍、拍间移动插值与事件触发的建设操作；继续沿用，不把战斗改成每秒30/60次结算。

| 层次 | 更新依据 | 边界 |
|---|---|---|
| 输入与镜头 | 收集输入，显示帧消费最新状态 | 悬停可合并；拖动/旋转的位移要累计，不能丢位移；点击、松手、取消等命令按顺序保留 |
| 建设与经济命令 | 实际点击或应用参数 | 即时校验并反馈，不等下一战斗拍，不在每次渲染时重复执行 |
| 战斗逻辑 | 现有战斗节拍、速度与暂停规则 | 伤害、出兵、合流、寻路和结算只由游戏状态推进；不依赖渲染帧数或镜头位置 |
| 视觉插值与动效 | 显示帧读取游戏时间和逻辑结果 | 镜头、敌人位移、炮火、HP锚点与建设预览连续更新；人物步态不是独立人物模拟 |
| 环境表现 | 云雾等现有环境时钟 | 沿用各自暂停语义，不擅自统一冻结或继续；运动不改变视野权限 |
| 静态派生数据 | 对应依赖真正变化 | 建筑边缘、街景摆放、控制轮廓等不因转镜头或敌人走一步全部重算 |

`requestAnimationFrame`跟随显示刷新机会，并不保证60Hz；插值应使用时间戳，不能按“每帧前进固定距离”实现。[MDN说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

### 每显示帧最多一次悬停拾取（建议）

- 高频`pointermove`只记录最新坐标、累计镜头位移及输入脏标记；同一显示帧最多执行一次悬停射线和预览更新。没有指针、镜头、命中对象或相关权限变化时可复用结果。
- 指针静止但镜头、建筑或建设资格改变时，也必须更新悬停；缓存不能只依赖鼠标坐标。
- 纯旋转不做建设拾取；平移拖动可暂缓悬停，松手立即恢复。未来若支持拖画墙体，应保留路径经过格，不能只保留最后一个格。
- 点击是准确性例外：按点击/松手坐标及最新相机、对象矩阵重新确认目标，并用当前状态执行完整建设校验；不能直接提交上一帧缓存的合法点。不能因合并悬停漏掉快速点击、把点击拖成建设，或在旧相机位置建造。
- 保持当前浏览器主线程与一个显示循环即可。独立`setInterval`、Worker、高频固定逻辑循环和通用命令框架，均不是这次优化的前置条件。
- 慢帧、暂停、倍率和切后台继续保持现有结算顺序；当前帧循环会限制累计时间，本轮不调整。以后若处理积压战斗拍，不能靠跳伤害/跳出兵追时间，也不能切回前台后一次补算大量战斗而卡死。

## 2026-10-14分析基线

### 浏览器观察

参考分析时HEAD为`e116176`。在Codex内置浏览器、1280×720页面、默认seed `cityx-01`、自然地形开启下，使用独立测试页及现有绘制统计；原试玩局未重置。未记录完整硬件、浏览器版本与GPU轨迹，因此只是本机问题定位记录，不作为跨设备基准。

| 场景短窗口 | 绘制函数平均/P95 | 3D提交 | 面数/视觉人物 |
|---|---|---:|---|
| 第一天，自由正交，200% | 约5.0/6.0ms | 724 | 约258k/0 |
| 第七天，自由正交，选炮，200% | 约6.8/10.2ms | 751 | 约258k/0 |
| 第七晚，自由正交，313%，暂停选炮，已有炮位 | 约17.5/26.2ms | 635 | 约242k/48 |

场景的朝向、缩放、状态及采样时刻不同，**不是受控A/B**，不能把差值归因于增加48个人物。旋转附近短窗口还出现过更高耗时，需固定场景再测。`paintMap()`计时不含全部输入事件、战斗更新、布局合成或GPU完成时间；平均耗时也不能直接换算成真实FPS。当前统计改变角度即清空窗口，不适合评价连续旋转的P95。

### 纯逻辑局部测量

同一默认地图，第七天、1000金币、6人口、146个地块、86个合法远炮候选；使用本机Node，预热5次、测40次。测量脚本只在终端运行，没有加入模拟玩法或持久诊断框架。

- 重建`createTowerOverlay`并首次执行`eligible('B')`：一次测量中位约18.2ms、P95约25.8ms。
- 后续拆分测量：白天辅助层约2.75ms、首次资格约9.17ms；夜间辅助层约3.49ms、首次资格约12.88ms，均为中位数。两轮受预热及运行环境影响，不能当作同一次耗时相加比较。
- 读取已缓存资格结果接近零开销；数字参数校验本身很轻。尚未量化浏览器反复读控件/复制参数的成本，不能把它说成已证实的最大瓶颈。
- 当前敌人开始/完成移动经`update()`清空`mapView`；选炮时会重新创建辅助层和资格缓存。因此存在值得优先处理的重复计算，但实际改善幅度仍须浏览器前后对照。

旧迁移文档中的静态大城专项数据不包含本轮完整UI、敌人交互和地形负载，不能拿它证明当前运行应当流畅。

## 后续3D实现约束（助手建议；用户优先级适用于全部方案）

| 领域 | 实现约束 | 必须保住的表现/行为 |
|---|---|---|
| 缓存与状态 | 按实际依赖失效；几何/控制资格与敌人占用、金币、悬停分别处理。参数在输入/应用/取消时更新，一帧共享同一份参数与相机描述 | 不丢草稿预览；建拆、失控、金币变化后资格和报价立即正确；实际操作仍重新校验 |
| 渲染职责 | 显示只消费状态，不推进经济/战斗；相机变化只更新投影、可见范围及必要的照明/像素尺度 | 三种视角与正交/透视权限、伤害、命中一致，完整保留原有手感 |
| 模型与材质 | 重复资产共用可共享的几何/贴图/材质；能实例化或按空间块合批的静态内容优先复用；动态转向/后坐部分保留独立节点 | 配色差异、废墟关联、窗灯、法线、轮廓和真实尺度一致；不为合批抹掉美术细节 |
| 空间组织 | 合批保留合理空间粒度，避免全城一包导致无法离屏剔除；拾取用候选列表、图层和简单代理，装饰先排除再检测 | 保守包围体覆盖树冠、光柱、粒子和阴影贡献；镜头边缘不突然消失；不能裁掉屏外照进来的灯 |
| 静态与动态 | 静态矩阵、屋顶采样、街景摆放、几何合并、材质绑定只在相关对象改变时做；动态更新只访问已登记节点 | 建筑恢复/拆除时立即呈现正确形态；暂停恢复、重试和昼夜切换不残留旧状态 |
| 光照与阴影 | 保留真实路灯照明，优先复用稳定光源池、筛掉对画面无贡献的灯；照明与投影分开评估，静态阴影按依赖刷新 | 暖色运营道路、冷色探照灯、火焰闪烁及近景受光连续；投影者/受光面变化或灯光移动时正确刷新，不能留下旧阴影 |
| 资源生命周期 | 炮火/火焰等频繁效果复用对象和缓冲，避免逐帧创建几何/贴图或改Shader结构；只上传变化且实际使用的数据 | 不漏掉真实开火/受击；变速和暂停不跳动画；共享资源不能被单个对象释放 |
| 画布与雾 | 每个渲染通道、整屏拷贝和纹理上传说明用途；静态层与动态层分别更新，无贡献通道跳过 | 保持路线在实体下、HP在实体上等既有层次；S0–S3、云纹运动、敌人渐隐、昼夜过渡不改变 |
| 更新频率 | 先复用不变结果，再考虑对低频变化数据降低计算频率并连续插值；镜头、选中反馈和关键战斗表现不随环境低频刷新受限 | 不能出现输入迟滞、步态/火光变卡、灯光跳亮或雾层闪烁；有可见损失则撤回该方案 |
| 新视觉功能 | 接入时写清触发条件、是否需要每帧工作、对象/材质/光源/通道增长方式、复用与释放方式，并检查真实主图 | 不以任意面数、提交数或灯数硬指标否决美术；发现超预算先定位浪费，视觉变更另行讨论 |

先由游戏状态决定信息权限，再决定渲染和拾取候选；隐藏对象不能通过命中代理、灯光、阴影或标记泄露。离屏只省显示工作，敌群仍按原规则移动/攻击。视野缓存须覆盖昼夜、瞭望塔、炮位以及敌源揭示/肃清等依赖，不能只检查控制区；首次出兵、失去视野或销毁源头后应立即更新信息状态。

Three.js说明了[合并对象减少提交](https://threejs.org/manual/pages/optimize-lots-of-objects.html)、[射线候选/图层过滤](https://threejs.org/docs/pages/Raycaster.html)和[阴影的额外渲染成本](https://threejs.org/manual/pages/shadows.html)。这些提供实现方向，不能代替本项目实测；合批、实例化、代理和分块均需验证画面及拾取一致性。

暂不引入延迟/集群照明、自制渲染器、全面ECS、逐人物物理、通用多线程调度或复杂自动画质系统。出现现有实现难以解决的实测瓶颈时再单独评估。

## 优化顺序与验收

以下为优化顺序，完成状态以末尾记录为准，不将分析计作完成。

| 顺序 | 工作 | 验收重点 |
|---|---|---|
| 0 | 修正统计窗口，区分输入/逻辑、派生数据、3D准备/提交/拷贝和显示帧间隔 | 连续旋转不清空采样；冷启动、首次建造尖峰与稳态分开记录，不拿CPU提交冒充GPU完成 |
| 1 | 保留静态炮位/地块缓存，敌人占用与资金变化增量更新 | 有敌人时选炮不周期性重算整城；当前格、将进入格、容量/银行信用/加急费仍正确 |
| 2 | 每显示帧一次悬停拾取，复用参数/相机和静态场景描述 | 快速移动、拖动、松手、点击、旋转后点击不丢操作、不误建，不引入悬停延迟 |
| 3 | 去除无意义遍历/材质绑定/矩阵更新，减少无贡献画布通道和上传 | 画面同层次、同颜色、同雾与同动效；逐项对照收益，避免一次重写渲染架构 |
| 4 | 定位建造尖峰、街景整组重建、光源变化和剩余GPU开销 | 局部变化不无故重建整城；现有真实灯光、投影与清晰度保留；不默认降分辨率/人数 |

### 测量与停止条件

- 同一seed、日期、布局、敌人进度、视角/角度/投影、缩放、窗口、像素比、灯光/人物配置进行前后对照；记录浏览器和设备。固定同一暂停战局便于比画面，活跃战斗另测更新尖峰。
- 最少覆盖：自由旋转和平移；夜间有敌人时选炮/悬停/实际补炮；有运营路灯与探照灯的城区；近景及全图。另检查昼夜过渡、重试及连续建拆后的资源是否持续增长。
- 记录显示帧间隔P50/P95、偶发长帧及输入到预览的延迟；渲染调用数、三角面、光源数、纹理/几何数量用于定位，不能单独代表性能。空闲20Hz环境刷新与交互掉帧分开判断。
- GPU数据在确有需要时用浏览器性能工具或可用的异步计时分析；不逐帧强制等待GPU，也不为测量另造地图/战役。诊断功能应可关闭，避免测量本身占满主线程。
- **建议目标，非用户已确定门槛**：代表桌面环境的镜头操作争取接近60帧，较弱设备战斗争取稳定30帧；16.7/33.3ms是整帧预算，不能全部分给`paintMap()`。不承诺当前设备已达到，也不通过默认降画质达标。
- 采用同机同镜头截图及运动对照：建筑细节、真实光源影响、探照灯、火焰、弹迹、人群密度/步态、云雾渐隐、路线/HP与建设预览无可感知退步，且权限与结算不变，才接受优化。
- 实际卡顿消除、操作连续且视觉不退步后回到试玩；没有新瓶颈不继续追逐更低面数、更多FPS或完整平台适配。性能通过不等于游戏已被认可好玩。

## 实施记录

### Step1：炮位资格与参数缓存（2026-10-14，已接入）

- 建筑辅助层和不含敌人占用的炮位资格跨战斗更新复用；敌人所在/将进入格只做集合过滤。静态签名覆盖建筑、控制/探索、参数、阶段/日期、来源保留、经营/人口和可用资金；重试的新状态单独重建，实际点击仍执行原`placementError`。
- 实验控件读取和有效预览参数复用到输入/应用/取消或参数基值、阶段/波次变化；显示预览独立复制，不能写回玩法草稿。
- 同机同进程、默认第七晚地图、60次敌人位置变化局部对照：每次新建辅助层并计算远炮资格，中位4.677ms/P95 5.271ms；复用后含签名检查与占用更新，中位0.120ms/P95 0.143ms。该轮预热/负载与前期样本不同，只比较这组配对结果，不换算为整帧提升。
- 285项测试通过，新增跨移动复用及资金/建设/经营/参数/探索/阶段/重试失效检查，与原全格真实校验对照。浏览器第七天1000金币下，错误玩法草稿不阻挡透视/FOV视觉应用，取消玩法草稿不回退视觉，合法屋顶炮位显示正常；画面记录`/private/tmp/cityx-performance-cache.png`。未减少模型、人物、光源、云雾或清晰度，完整动态战斗/拾取优化继续下一步验证。

### Step2：悬停按帧合并与当前相机拾取（2026-10-14，已接入）

- `pointermove`只保留最新悬停坐标，显示回调最多消费一次；拖动仍累计全部位移，平移/旋转期间不做建设悬停，松手恢复。指针离开/取消清除待处理输入，逻辑更新、镜头和窗口变化会刷新静止指针的结果。
- 点击仍立即按松手坐标确认；拾取与绘制共用相机配置并更新矩阵，旧相机的屏幕吸附点不参与新视角点击。透明特效和标明装饰的非地面网格在射线检测前排除，复用射线及命中缓冲；未增加独立逻辑循环或修改战斗节拍。

- **待实施建议**：启动时准备有限的材质/灯槽组合；选工具或有效预览时提前准备下一档组合，确保完成后才首次显示该结构；灯槽按经实测的小档位增长，避免每新增一塔产生全套新程序。预热不能偷偷推进游戏状态，不能靠长期堆满零强度灯解决；视野/道路局部更新列为后续独立项。验证应覆盖白天/夜间建生产、住房、首塔/第二塔、预览取消及之后的旋转，分别记录冷启动与已有驱动缓存的结果。

**缓存与预热分别解决不同问题**：

### 跨场景调整方案：稳定照明结构与提前准备（2026-10-16，助手设计，待实施/实测）

**2026-10-17实施状态**：用户确认利用白天建设到入夜之间分批准备；核心昼夜分离、独立代表材质、增量队列及启动准备已接入，见Step16。下文的小档容量和控制/道路局部更新仍是候选，没有一并实现；不将设计表当作全部完成清单。

**整体判断**：保留Step1–9的依赖缓存、每帧拾取合并、静态节点/描述复用和按实际灯具控制规模；保留Step15的敌人实例颜色预建及镜头不反复增减灯数。调整Step15的全天零强度夜灯、逐设施扩容，以及Step12先绘制再空闲补编译的覆盖范围。只回滚灯槽会重新引入夜战旋转尖峰，只增加预热又无法控制长期逐灯开销，须一起验证。

**按昼夜玩法收敛准备范围（用户2026-10-16提出利用阶段差异，以下为助手建议）**：实际操作入口在夜间只允许补近/远炮，不允许生产、住房或瞭望塔建设，因此夜间新建路灯/塔灯不必作为常规扩容路径。白天建设立即显示楼体、塔与灯杆，夜间专用光源不参与白天着色；每次真实建设后标记夜景依赖变化，连续操作合并为最新布局，分小批准备当晚照明。加载阶段准备基础昼夜组合；不要等长按结束白天才启动编译，也不靠延长按钮动画掩盖准备。长按期间虽仍处白天规则，却已经预演夜光，故必须按实际过渡进度使用夜景组合，取消时按原动画回退。

白天篝火/燃烧车辆仍有真实火光，首次预览/楼体材质也仍需准备；夜间补炮的材质/炮火要提前覆盖，镜头移动、敌源揭示或其他显示变化仍可能产生新资源。阶段分工可简化通常路径，不能保证夜间永不变化，亦不因此新增建设限制。先实施这条围绕现有玩法的准备流程，再由实测决定是否需要更多容量档位与提前量，避免一开始设计覆盖任意夜间建设的通用系统。

**建议采用两套稳定照明配置，沿用现有Three渲染器与游戏状态**：

| 场景/事件 | 建议行为 | 必须避免 |
|---|---|---|
| 正常白天 | 只让实际白天火光所需的点光槽参与着色；夜间专用路灯/塔灯保留对象但不参与当前光照结构 | 长期为整片城区的零强度夜灯支付逐灯计算 |
| 长按预演、夜晚及日出过渡 | 使用已准备的夜间照明配置；按原进度连续调整光强、窗灯与扫光，完全回到白天后才切回白天配置 | 在过渡中按亮度阈值反复增减灯数；取消长按造成光线跳变 |
| 平移、旋转、缩放 | 各配置容量保持稳定，只换槽位所属设施、位置、方向和强度，保留原换位渐变与贡献范围 | 按每一帧屏幕内灯数改变着色器；漏掉屏外照进来的光 |
| 白天建设/夜间补炮 | 白天立即显示实体并更新待准备夜景；夜间补炮使用提前准备的正式/预览材质，必要的新组合仍可补充准备 | 白天每建一座塔就改变当前夜灯结构，或漏掉夜间补炮的首次材质 |
| 拆除/失控 | 原规则立即熄灯、空槽可复用；不因单次拆除立即缩容 | 建拆交替反复编译；保留旧主人照明或泄露未知区域 |
| 重试/新局 | 取消过期任务、释放旧局资源并按新状态重建准备记录 | 旧异步任务完成后覆盖新局；永久积累历史灯峰值/预热资源 |

- **容量按小档位增长，具体数值先测再定**：初始容量以当前真实灯具和少量余量为依据，不恢复“没有路灯也开24槽”。普通加一塔应尽量落在现有档内；需要扩容时在用满前预热下一档。火光/路灯/塔灯继续保留原颜色、强度、照距和所有权，第一步不合并各类灯的分配代码。预热按实际总点光/聚光数量及材质特征去重，减少无意义组合。
- 预留是计算与编译间的取舍：零强度空槽仍有成本，档位越大不一定越好。保留配置中的路灯预算，但不新增会截断本应可见火光或探照灯的硬上限；超出已准备容量仍须正确显示，记录未命中场景，不宣称任意规模都零卡顿。若引入可调新参数，按P0同步config、实验面板与校验。
- 两套配置表示有限的灯光结构，不是两张地图或两套游戏状态。光强/位置等连续参数变化无需逐值编译；实际受影响的材质、实例属性、施工遮罩、单双面、透明及阴影条件必须与正式绘制一致。白天配置增加了常态节省机会，也增加了需要准备的组合；须与“全天同一小档槽位”同场景对照，只有收益抵过新增准备成本才保留此拆分。

**准备流程与资源约束**：

1. 启动加载43个模板后，用现有模型构造函数产生少量真实代表：普通/特殊建筑的完好与废墟、修缮预览与原楼施工遮罩、设施、升级、零人数敌人。先覆盖当前白天和首批夜间组合，再完成必要上传/离屏试绘，准备完成后展示首帧；不逐栋实例化未知全城或推进任何探索/经济/战斗。
2. 后续按实际依赖增加准备任务：灯槽接近容量、首次选择一种尚未覆盖的工具/材质、真实状态变化。选工具和有效悬停是提前准备机会，不能假设玩家一定悬停足够久；快速点击、键盘切工具、夜间直接建设也要验证。签名已就绪时直接复用，不在每帧/每栋重复编译整城。
3. 下一档使用独立的准备容器/目标照明场景，沿用同一renderer和真实材质结构；不把未来灯槽临时挂入正在显示的场景。每次只提交一小批有缺口的材质，任务去重并按当前交互优先；实际战斗、相机和输入继续执行，不用全局暂停掩盖准备开销。
4. `compileAsync`并不表示调用过程完全不占主线程。本地Three源码先同步执行`compile`再轮询就绪；分批提交也不能保证任意设备单批固定低于某个毫秒数。优先使用并行编译能力，记录提交耗时；没有扩展时不承诺无阻塞。必要上传与完整分辨率首帧另验，不能用小尺寸试绘推断真实像素负载。[官方编译接口说明](https://threejs.org/docs/pages/WebGLRenderer#compileAsync)
5. 预热代表材质需在实际使用接管前保留必要引用；本地Three在程序引用数归零时会销毁程序，不能刚预热就释放掉唯一持有者。保留当前/必要昼夜及下一档的准备资源，切换完成后清理无用代表，沿用编译期间延迟释放保护；避免保存每次历史建设的整份场景。异步轮询材质不应同时被其他任务切换至另一未核对组合；队列串行，按签名记录完成，取消/新局用版本校验。
6. 未命中组合时继续保证实际规则、反馈与正确照明，不默认延迟扣费/建设、隐藏新塔光或冻结战斗。这条兜底仍可能产生首次准备尖峰，需如实记录，再决定是否补充有限覆盖；预热不能让有限硬件支持无限灯数或任意模型。

**分步实施建议，每项独立验证并按P0记录**：

- 第一项：修正“首次显示之后才预热”的顺序与覆盖，准备首批正式/预览材质和必要灯数组合；暂不同时重构道路或场景，确认白天建塔尖峰下降且旋转收益保留。

### 当前Web规模与未来Godot渲染判断（2026-10-16，仅分析，未运行Godot）

**当前规模判断**：模型资源小，几何量尚属可管理范围，提交/合成方式和首次准备更值得优先排查。不能仅凭场景low poly或模型4.91MB断言GPU负载低，也不能把当前秒级尖峰当成Web无法承担此类城市。

| 维度 | 已知事实 | 判断边界 |
|---|---|---|
| 地图与资产 | 默认60×60逻辑格、146个地块，43个GLB共4.91MB | 不是3600个独立模型；文件体积不等于显存，全城扩张后实际几何还会增长 |
| 几何与提交 | 既有不同场景采样约24～35万三角面、600～900次3D提交/次重绘 | 含实际渲染通道与阴影工作，不是纯主视图独有模型数量；对桌面并非显然超量，但提交较分散，弱设备需测 |
| 照明 | 路灯默认预算24；近期旋转对照为8个点光/1个聚光，火光/塔灯按峰值增长 | 24不是全场灯数上限；扩大控制区/多塔后的重叠照明未完成极限测试 |
| 分辨率与合成 | DPR上限2，太阳阴影2048²；城市与敌人分层绘制并拷贝到Canvas后叠加信息，敌人空时省略其通道 | DPR1→2将主视图像素数变为4倍；多层拷贝、透明雾及特效有填充/带宽成本。代码事实不代表已测出各项占比 |
| 人物 | 实例池上限2048，已有对照实际可见0/16，早期窗口48 | 容量不等于同时绘制人数；不能据此承诺2048个完整动画人物的战斗性能 |
| 实测 | Step15固定夜战旋转窗口中位4.1ms、最大8.0ms；建设首塔仍有约1.37秒绘制尖峰 | 为本机局部CPU/驱动调用计时，非GPU利用率；缺少完整硬件与独立GPU时间，不外推全部浏览器/手机 |

**Godot提供的能力**：以下按查询时官方stable文档说明，正式开工应按选定版本/目标设备复核；未进行同场景Godot移植或性能实测。

- Forward+采用集群前向光照：先把灯分配到视锥内的小区域，像素只计算可能影响该区域的灯，适合桌面多局部光源。它有更高的基础成本；灯光范围过大、重叠很多、阴影和透明效果仍会增加工作，不能将“支持很多灯”解释成“每盏灯免费”。此处不需要默认照搬Web用实际全局灯数生成变体的调度办法。[官方渲染架构](https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html)
- Mobile也能用于桌面，简单场景/部分集显可能更合适；Compatibility覆盖旧硬件，且目前Godot Web导出只能使用它。Forward+不是任何设备上都更快，把当前原型换成Godot Web也不会自动获得桌面Forward+能力。若正式版优先现代桌面，建议先用Forward+验证既定灯光/美术；低配及移动端需求明确后再比较其他管线，尚非用户已确定的平台选型。[渲染器比较](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
- Forward+/Mobile从Godot4.4起有ubershader与加载阶段管线预编译，减轻首次组合卡顿；仍需让引擎在加载时接触实际网格/材质/特效和使用的渲染特征。Compatibility不享有同一预编译机制。不能预设新特效、运行中更改渲染特性或资源加载完全无尖峰。[管线编译说明](https://docs.godotengine.org/en/stable/tutorials/performance/pipeline_compilations.html)

**正式开发时先落实的资源组织，保留现有视觉目标**：

1. 共享模型/材质资源；树木、路灯杆、同类街景和视觉人群优先实例化，按空间区域分组，避免每个颜色变体复制全部材质。Forward+对符合条件的同mesh/材质不透明对象支持自动实例化，不能假定透明建筑预览也自动合批。[官方3D优化](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)
2. 大量重复物件可用MultiMesh，但它按整组剔除，不自动逐实例剔除；全城一个MultiMesh可能让看不到的内容也提交。区域粒度和实例动画方式应由实际镜头、数量与美术需求决定。[MultiMesh说明](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)
3. 路灯保留真实局部光源、探照灯保留真实扫光与光柱；合理设置实际照距，使照明覆盖匹配视觉需要。窗户自发光/屋面受光与真实投影灯分清职责；自发光并不默认照亮邻近道路。真实照明与阴影分别预算，先沿用Web仅主光投影、局部灯不投影的效果基线；若正式版增加遮挡投影，作为新视觉功能单独测，而非一键给所有灯开阴影。[灯光与阴影](https://docs.godotengine.org/en/stable/tutorials/3d/lights_and_shadows.html)
4. 城市直接在引擎3D视口呈现，路线/标牌/雾按既定图层组织；没有视觉理由不复刻Web的多次WebGL→Canvas整屏拷贝。大面积透明雾、火光和光柱的覆盖面积/叠层仍需检查；俯视能看到大片城市，遮挡剔除的收益可能低于街道内第一人称，不能只依赖引擎自动遮挡。
5. 保留逻辑敌群与视觉人物分离，不为每个人物额外增加导航、碰撞与独立伤害结算。正式人物若改为独立骨骼动画，属于新增负载，不能用当前简模实例测量为其背书。

**结论边界**：对普通现代桌面硬件，现有场景是合理的Godot3D开发起点，没有证据要求先削减建筑、灯光或画面；这是基于规模和管线能力的判断，不是已验证FPS。正式版新增高精模型、全动态阴影、体积云/GI、更多同时可见敌人或更大地图时须重测。先依靠引擎现有剔除、资源共享、实例化和预编译，把目标场景做出并用内置CPU/GPU分析器检查；没有实测瓶颈不提前自研照明、流式世界或通用优化框架。本轮只记录分析，没有修改Web运行代码或旧Godot项目。

### Step16：白天建设后分批准备昼夜材质（2026-10-17，已接入）

**原因与范围**：修正Step15白天新建路灯/瞭望塔也增加当前着色灯数的副作用，利用主要建设发生在白天的实际玩法提前准备夜景。本轮不修改建设权限、扣款、伤害、视野、长按时长或昼夜动画，不增加灯数档位或重构道路。

- 白天路灯及塔灯不参与当前着色；篝火与燃烧车辆的白天照明保留。预演夜光、正式夜晚及日出期间按原进度渐亮/渐灭，完全回到白天后退出夜灯组；镜头移动仍只调整强度/位置/方向。空槽随组一起切换，拆塔后不会残留白天聚光计算，也不会因空槽归属改变夜间峰值灯数。
- `city-shader-samples.js`按本原型实际材质/几何结构去重，创建昼夜独立目标照明和代表材质，保留原shader回调/纹理引用。准备对象不进入真实场景；真实材质不会被预热切换`currentProgram`，避免显示帧干扰Three的异步就绪轮询。颜色、位置和光强变化不新增结构；无用旧照明组合在新准备完成后释放。
- `city-shader-warmup.js`合并连续建设为最新布局，每次空闲只提交一个代表对象，上一批异步就绪后才排下一批；中途布局变化会跳过旧任务剩余批次。已经完成的结构复用。编译中的资源延迟到当前批次结束释放，重试/重开用版本取消旧任务；夜间仍可补充必要准备，不再因进入夜晚直接丢弃未完成任务。
